# 白杖振動デバイス：チーム実装仕様・分担ガイド

更新日：2026年10月17日 / 対象：Mac 2人・Windows 2人 / 状態：実装前の共有仕様 v0.1

> **作るもの：iPhoneが胸・頭の高さの障害物を検知し、BLEで白杖へ通知して、黒いグリップ内のモーターを振動させる。**
> 既存の検知コードを利用する。BLE・ファームウェア・電池回路・グリップ一体化は追加作業。
> 本書の「提案」は、この資料で具体化した実装案であり、実装済み・実機検証済みという意味ではない。

## 1. 最初にチームで共有すること

| 区分 | 内容 |
|---|---|

| 今回の機能 | iPhoneで検知 → BLEで危険度送信 → グリップの振動で知らせる |
| 最新の電源案 | 単3アルカリ電池2本で基板とモーターを駆動。XIAO用に昇降圧回路を追加 |
| 最終的に目指す機構 | 電池・回路・モーターが黒いグリップ周辺にまとまる構成。既存グリップ内へそのまま収まるかは未確認 |
| 最初の完成形 | 卓上または仮ケースで、実際の障害物検知からモーター振動まで一通り動作する |

## 2. 全体の流れ

```text
首掛けiPhone（画面は身体側、背面カメラは前方）
  │ AVFoundation：深度を取得 / Core Motion：重力・傾き
  ▼
既存のHeadLevelGeometry：進路上の胸・頭の高さの障害物を判定
  ▼
追加する状態生成処理：注意・危険・検出なし・検知不能を整理
  │ Core Bluetooth / BLE GATT
  ▼
XIAO ESP32C3：受信・期限確認・振動パターン生成
  │ D1（GPIO3）をHIGH/LOW
  ▼
DRV8835：モーターへの電源をON/OFF
  ▼
黒いグリップカバー内のコイン型モーター → 指・手に振動
```

スマホと白杖の間に電線は不要。首掛けホルダーは背面カメラを塞がず、歩行中の揺れ・反転・下向きを抑える。カメラの向きが進行方向と違えば、検知領域もずれる。

### 胸・頭の高さ検知の初期値

| 項目 | 現コードの初期値 | 意味 |
|---|---|---|
| 前方距離 | 0.3〜2.5m | この範囲の深度点を対象 |
| 進路幅 | 中心から左右各0.45m | 合計0.9m |
| 床からの高さ | 1.0〜2.0m | 利用者の身長に自動追従する実装ではない |
| 危険 | 2.0m以内 | `.danger` |
| 注意 | 2.0m超〜2.5m | `.caution` |
| 深度点数 | 12点以上 | 高さ・進路条件を満たす点が必要 |
| 深度処理間隔 | 少なくとも0.2秒 | 最大約5回/秒。実際の取得頻度は端末依存 |
| カメラ高さの初期値 | 1.3m | 床が推定できない場合に使用。設定値は保存される |
| 音声警告の継続判定 | 2フレーム | 即時の単発ノイズを抑える |
| 音声の再通知間隔 | 5秒 | 外部振動の更新周期には流用しない |
| 近接ブザー | 1m以内 | 現コードの音通知。外部モーターとは別 |

これらは定数の初期値であり、端末の保存済み設定と一致するとは限らない。首掛け位置と利用者に合わせて確認する。1mより近くても新しい第3の振動段階は今回追加せず、まず既存の注意／危険で統一する提案。

### 今回の追加で特に直す境界

- `HeadLevelAnnouncer`は音声の再通知制御。ここからだけBLE送信すると5秒間隔などに制限されるため、深度結果から独立して外部通知状態を生成する。
- `hit == nil`だけでは検知不能と検出なしを区別できない。無効姿勢・深度欠損・停止・最新フレーム時刻を持つ状態へ拡張する。
- `HeadLevelGeometry.axes(...) == nil`時は現在`hit=nil`の結果を返す。この結果をCLEARへ変換しない。
- カメラ側はnil結果を`onDepth`へ転送しない経路がある。最後の有効フレーム時刻だけでなく、明示的な取得エラーも外部状態へ伝える。
- `App/JunctionGuideApp.swift`は背景移行で`store.pause()`を呼び、カメラ等を停止する。前面復帰後は新しい深度を得るまで検知不能とする。

現在のXcodeプロジェクトは最低iOS 26.0、Swift 6.0。Mac側はこのターゲットと接続iPhoneを扱えるXcodeを使う。具体的なXcode版・ESP32ボードパッケージ版は開始時に全員で記録する。

### Mac側の開始手順

1. Gitで同じ基準のソースを取得し、現在の変更差分を確認する。
2. `Config/Local.xcconfig.example`を`Config/Local.xcconfig`へコピーし、自分の`JG_TEAM`と固有の`JG_BUNDLE_ID`を設定する。秘密・署名情報はGitへ入れない。
3. `JunctionGuide.xcodeproj`を開き、Scheme `JunctionGuide`を選択する。
4. iPhoneの開発モード・信頼・カメラ許可を確認。深度ステータスと実際のデータ取得を確認する。
5. Bは`NSBluetoothAlwaysUsageDescription`を追加する。Bluetoothの拒否・電源OFFは接続画面で区別する。
6. モデルファイルはGit対象外。既存の全機能を再現する場合は`Docs/MODEL.md`と`Scripts/install_model.sh`を確認する。モデル未導入と深度非対応を混同しない。

### 無料Apple Account

Personal Teamで自分のiPhoneへ開発用インストール可能。プロビジョニングは発行から7日で期限切れとなり、再ビルド・再インストールが必要。10 App IDs、3 devices、1台あたり3 appsの制限あり。TestFlight／App Store配布は有料プログラム側。デモ前日に再インストールする。

## 7. BLE通信・振動の共通仕様

詳細・バイト例は [BLE_PROTOCOL_DRAFT.md](BLE_PROTOCOL_DRAFT.md)。以下は並行実装のための提案値で、B/Cが実装開始時に同じ版へ固定する。

| 項目 | 提案 |
|---|---|
| 役割 | iPhone=Central、XIAO=Peripheral |
| Device name | `CaneVibe-01`。名前だけを機器識別に使わない |
| 発見方法 | 専用Service UUIDをAdvertisingに含め、iPhone側でフィルター |
| Command | 10バイト固定 / Write with response |
| Status | 10バイト固定 / Read + Notify |
| 状態 | 0=検出なし、1=注意、2=危険、3=検知不能 |
| 送信周期 | 接続中250msを目標、状態変更時は早めに送信。Writeを無制限に積まない |
| フレーム鮮度 | 最終有効深度が600msより古ければ検知不能へ |
| 指示の有効期限 | 受信から1,000ms。期限切れ・切断で危険振動を停止 |
| 認証 | 管理されたデモ環境で手動選択。暗号化・Bonding設計は未決定。公開利用対応とは扱わない |
| 電池残量 | 最初の版では表示しない。電圧測定回路は現在の購入リストにない |

検出なしは「有効な範囲内で対象が検出されなかった」という意味で、周囲の安全保証ではない。音声の5秒クールダウンをBLE更新に流用しない。

### 振動パターンの提案

| 状態 | 提案パターン | 備考 |
|---|---|---|
| 検出なし | OFF | 新しい有効判定だけで到達 |
| 注意 | ON 150ms → OFF 850msを反復 | 状態が続く間だけ |
| 危険 | ON 200ms → OFF 150msを反復 | 注意より高い頻度 |
| 検知不能／切断／TTL切れ | 危険振動を停止。必要なら50ms×3回を一度だけ | 動作不能の通知パターンは利用者確認で最終決定。繰り返し再生しない |

同じ状態の250ms更新で毎回パターンを先頭に戻さない。状態変更時だけスケジュールを切り替え、受信処理を`delay()`で長時間止めない。1個のモーターで左右方向を伝える仕様は今回設けない。

## 8. 回路・組立条件

[全体回路図](cane-circuit.png) / [拡大用SVG](cane-circuit.svg) / [詳細接続表](cane-circuit.md)

```text
単3アルカリ2本（公称3V）→ スイッチ → VBAT
  ├─ TPS63802（5V設定）→ 1S4 → XIAO 5V
  └─ DRV8835 VM → OUT1/OUT2 → モーター
XIAO 3V3 → DRV8835 VCC
XIAO D1 / GPIO3 → DRV8835 IN1
DRV8835 IN2・MODE → GND
全てのGND → 電池－
```

- D1という名前は「XIAOのD1端子」と「回路図のダイオードD1」の2か所で使われる。配線時は部品名と端子名を区別。
- TPS63802のVR1を必ず取り付け、XIAO未接続で5.00Vに調整。ENは基板内プルアップにより未接続。JP1短絡で省電力とする案。
- 1S4の帯なし側(A)を電源出力、帯側(K)をXIAO 5Vへ。電圧降下後の基板入力を確認。
- DRV8835-PはIN/INモード。IN2=LOW固定、MODE=LOW、IN1=HIGHでOUT1=H/OUT2=L、IN1=LOWでHi-Z。
- LBV10B-009はブラシレス駆動回路内蔵・極性あり。逆転しない。初期版は秒単位ON/OFF。一般のブラシ付きモーター向けPWMをそのまま適用しない。
- USBデバッグ中は電池スイッチを切ってもXIAOはUSBで動く。電池が充電される回路ではない。
- モーターと無線送受信の負荷で電源が落ちないか測定。低電圧時の状態は未検証。ソフトウェアの電池監視は現状ない。

## 11. 電池持ちの扱い

現時点では測定値なし。単3×2本なら容量mAhは2倍にならず、直列で電圧が加算される。アルカリ電池の容量は負荷・終止電圧・温度で変わる。

以前の平均電流29.3mAは「50mAで5ms、27mAで45ms」という仮定の時間平均。通信間隔・実際の電流・給電測定点を確定した値ではなく、電池寿命の保証に使わない。

D/Cが測る項目：電池側の平均電流とピーク、電池電圧、昇圧後5V、XIAO入力、3V3、振動時の電圧降下。電池側でモーターを含めて平均電流を測れば、同じ電流をもう一度足さない。基板側で測る場合は電圧と変換効率を含めた電力で換算する。

```text
平均電池電流 = 測定区間の消費電荷 / 測定時間
基板入力電力 = 基板入力電圧 × その端子で測った電流
電池からの必要電力 ≒ 基板入力電力 / 電源変換効率 + モーター側平均電力
```

8時間動作は評価目標。現状の証拠で達成済みとはしない。

## 13. 必要な試験と記録

詳細は [TASKS_AND_TESTS.md](TASKS_AND_TESTS.md)。各試験は端末・iOS・アプリ版・FW版・電源・設定・期待結果・実結果・ログを記録する。

| 試験 | 合格の考え方 |
|---|---|
| 深度非対応／姿勢不正／カメラ停止 | CLEARではなく検知不能になる |
| 注意・危険・解除 | 状態に対応するパターンへ遷移。古い指示が残らない |
| 更新停止・アプリ背景・通信切断 | 白杖側で最後の有効指示から1秒以内を目標に危険振動が終了 |
| 再接続 | 最初は検知不能、最新判定後に再開 |
| 不正長・未対応版・無効TTL | 受理しない。GPIOは動かさず期限も延長しない |
| 電源ON／OFF・モーター負荷 | 意図しない振動、リセット、異常な電圧降下がない |
| 握り・折りたたみ・首掛け | 接合部やカメラを塞がず、配線の引張・ケースのずれがない |
| 振動体感 | 地面からの白杖の感触と、通知振動を区別できるか利用者と確認 |
| 連続使用 | 電池・iPhoneの発熱、検知欠損、BLE切断を記録 |

Status受信は「基板が指示を解釈した」証拠で、実振動を測った証拠ではない。モーターの振動センサーは搭載しないため、体感・動画・測定と区別する。

iPhoneとXIAOは別時計。両者の時刻をそのまま引いて片道遅延を求めない。iPhone側の送信→Status受信は往復相当の指標。障害物提示→実振動は動画等で同じ時間軸に載せる。
