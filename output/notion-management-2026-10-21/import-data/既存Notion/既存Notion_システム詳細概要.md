## 1. システム概要

### 1.1 目的

iPhoneの背面カメラと深度センサーを利用して、歩行者の胸・頭の高さにある障害物を検出し、Bluetooth Low Energy（BLE）を介して白杖のグリップ部分に搭載した振動モーターで通知する。

通常の白杖では検知が難しい、頭上や上半身付近の障害物に対する補助的な歩行支援を目的とする。

### 1.2 検知対象

- 頭の高さに突き出した看板
- 胸や顔の高さにある木の枝
- 壁から突き出した設備
- 歩行経路上に存在する上半身付近の障害物

### 1.3 システムの特徴

- 既存の障害物検知処理を活用
- 白杖側では画像処理を行わず、振動制御のみを実行
- BLE通信によりiPhoneと白杖を無線接続
- 危険度に応じて振動パターンを変更
- 通信切断や検知不能を通常の障害物検出状態と区別
- 既存の白杖のグリップ部分の筒内部にシステムを組み込むことを想定

## 3. iPhone側の処理

### 3.1 AVFoundation：RGB画像・深度データ取得

<b>役割</b>

iPhoneの背面カメラからRGB画像と深度情報を取得する。

<b>使用技術</b>

- AVFoundation
- <code>AVCaptureSession</code>
- <code>AVCaptureVideoDataOutput</code>
- <code>AVCaptureDepthDataOutput</code>
- <code>AVCaptureDataOutputSynchronizer</code>（必要に応じて使用）

<b>取得情報</b>

| 情報 | 用途 |
| --- | --- |
| RGB画像 | 周囲の状況把握 |
| 深度データ | 障害物までの距離測定 |
| カメラ内部パラメータ | 3次元座標計算 |

<b>注意事項</b>

- 使用端末が対象の深度取得方式に対応している必要がある。
- 深度データには測距範囲や精度の限界がある。
- 細い枝、透明物体、反射物体などは検知が不安定になる可能性がある。
- 通常のiOSアプリではバックグラウンド移行時にカメラキャプチャが中断されるため、動作状態の管理が必要。

### 3.2 Core Motion：重力・姿勢情報取得

<b>役割</b>

歩行中のiPhoneの傾きや姿勢を取得し、障害物の高さ推定に利用する。

<b>使用技術</b>

- Core Motion
- <code>CMMotionManager</code>
- <code>CMDeviceMotion</code>
- Gravity Vector
- Attitude

<b>必要性</b>

首掛けiPhoneは歩行中に前後左右へ傾くため、カメラ画像だけでは障害物の実際の高さを正確に判定できない。

Core Motionの情報を利用することで、カメラ座標系から重力方向を基準とした座標系への変換を行う。

<b>課題</b>

- 歩行による端末の揺れ
- カメラ方向と進行方向のずれ
- 装着位置の変化
- カメラの地面からの高さの推定

※重力方向だけでは進行方向は確定できない。

### 3.3 HeadLevelGeometry：障害物判定

<b>役割</b>

深度情報と端末姿勢を利用して、歩行者の胸・頭の高さに存在する障害物を判定する。

<b>想定処理</b>

1. 深度データを取得
2. 画素座標を3次元座標へ変換
3. Core Motionを利用して姿勢補正
4. 障害物の高さを推定
5. 進行方向上にあるか判定
6. 障害物までの距離を算出

## 4. 危険状態生成処理

### 4.1 HazardStateManager

<b>役割</b>

HeadLevelGeometryの判定結果を4種類の状態に変換する。

| 状態 | 値 | 意味 |
| --- | --- | --- |
| CLEAR | <code>0x00</code> | 検出なし |
| CAUTION | <code>0x01</code> | 注意 |
| DANGER | <code>0x02</code> | 危険 |
| UNAVAILABLE | <code>0x03</code> | 検知不能 |

### 4.3 検出なしと検知不能の違い

<b>CLEAR（検出なし）</b>

検出処理は正常に動作しているが、指定した検出範囲に障害物が見つかっていない状態。

<b>UNAVAILABLE（検知不能）</b>

カメラ、深度センサー、姿勢情報、判定処理などの問題によって、障害物の有無を正常に判定できない状態。

検知不能を検出なしとして扱わないことが重要。

### 4.4 状態の安定化

距離の測定値が変動すると、注意と危険の状態が頻繁に切り替わる可能性がある。

対策として以下を検討する。

- ヒステリシス
- 時間的平滑化
- 状態遷移条件の調整
- 危険状態への遷移を優先
- 危険状態からの解除には一定の確認時間を設ける

## 6. XIAO ESP32C3：BLE受信・振動制御

### 6.1 主な役割

1. iPhoneからBLEデータを受信
2. 危険状態を解釈
3. 受信時刻を更新
4. 通信タイムアウトを監視
5. 状態に応じた振動パターンを生成
6. GPIOからDRV8835へ制御信号を出力

### 6.2 使用端子

| 項目 | 内容 |
| --- | --- |
| マイコン | XIAO ESP32C3 |
| 使用GPIO | GPIO3 |
| 基板上の端子 | D1 |
| 出力信号 | HIGH / LOW |
| ロジック電圧 | 3.3V |

### 6.3 通信タイムアウト処理

BLE通信が停止した場合、最後に受信した危険状態を保持し続けない。

<b>初期設定例</b>

| 項目 | 設定値 |
| --- | --- |
| 状態送信周期 | 100ms |
| 受信データ有効期限 | 500ms |
| タイムアウト時 | 通信異常通知 |

```txt
BLEデータ受信
    │
    ▼
最終受信時刻を更新
    │
    ▼
現在時刻 − 最終受信時刻
    │
    ├─ 500ms以内
    │    └─ 受信状態を採用
    │
    └─ 500ms超過
         └─ 通信異常状態へ移行
```

※検知不能と通信異常は内部状態として分離し、通知方式を設計したい

## 7. DRV8835：モータードライバ

### 7.1 役割

ESP32C3のGPIO信号に応じて、振動モーターへの電力供給を制御する。

GPIOから直接モーターを駆動すると、電流不足やマイコン破損の原因になる可能性があるため、モータードライバを使用する

### 8.3 組み込み条件

- 白杖の操作性を妨げない

- 地面から伝わる触覚情報を妨げない
- 長時間使用しても不快感が少ない
- 配線や基板が握る動作を妨げない
- 電池交換が可能
- 防滴性や耐久性を可能であれば考慮する

## 9. 電源設計

    ├──→ XIAO ESP32C3
    │

### 9.2 注意事項

- モーターの定格電圧を確認する
- DRV8835の動作電圧を確認する
- モーターの起動電流を確認する
- LiPoバッテリーの過充電・過放電保護を考慮する
- 必要に応じてモーター電源用の電圧調整回路を追加する
- ESP32C3とモータードライバのGNDを共通化する

## 17. 結論

本システムは、<b>iPhoneを障害物検知・危険度判定装置、白杖側のESP32C3を振動通知装置として役割分担する構成</b>とする。

開発では、既存のHeadLevelGeometryを活用し、新たにHazardStateManagerとBLEManagerを追加する。

## 1. システム概要

今回のシステムは、<b>iPhoneのカメラで利用者の胸や頭の高さにある障害物を検出し、その危険度に応じて白杖のグリップ部分を振動させるシステム</b>です。

主に視覚障害者の歩行支援を想定しています。

通常の白杖は、地面や足元付近の障害物を確認するために使用します。しかし、以下のような障害物は、白杖で検知できない場合があります。

- 頭の高さに突き出した看板
- 顔や胸の高さにある木の枝
- 壁から突き出した設備
- 歩行経路上にある上半身付近の障害物

そこで、iPhoneで上半身の障害物を検知し、その情報をBluetoothで白杖に送信します。

利用者はスマートフォンの画面を確認する必要がなく、<b>白杖を握っている手に伝わる振動によって危険を認識できます。</b>

### システム構成

このシステムでは、役割を大きく2つに分けています。

| 項目 | iPhone | 白杖側デバイス |
| --- | --- | --- |
| 障害物の検出 | ○ | × |
| 障害物までの距離測定 | ○ | × |
| 障害物の高さ判定 | ○ | × |
| 危険度の判定 | ○ | × |
| BLE通信 | 送信側 | 受信側 |
| 振動パターン生成 | × | ○ |
| モーター制御 | × | ○ |
| 通信切断への対応 | ○ | ○ |
| 主な処理装置 | iPhone | ESP32C3 |

<b>重要なのは、ESP32C3側で画像処理や障害物検出を実行しないことです。</b>

高度な処理はiPhoneで行い、ESP32C3は受信した状態を振動に変換するだけにします。

これにより、白杖側の小型化、低消費電力化、ソフトウェア開発の簡略化が可能になります。

## 2. iPhone側の処理

### 2-1. AVFoundation：障害物までの距離を取得

AVFoundationは、iPhoneのカメラや映像処理を扱うAppleのフレームワークです。

今回のシステムでは、主に以下の情報を取得します。

Appleは、LiDAR対応機種で深度データを取得するための<code>AVCaptureDepthDataOutput</code>を提供しています。RGB画像と深度データを同期して取得することも可能です。[Apple Developer](https://developer.apple.com/documentation/avfoundation/avcapturedepthdataoutput?utm_source=chatgpt.com)

#### 深度データとは？

| 取得情報 | 内容 | 用途 |
| --- | --- | --- |
| RGB画像 | カメラの映像 | 周囲の状況の把握 |
| 深度データ | 各画素に対応する距離情報 | 障害物までの距離測定 |
| カメラ内部パラメータ | 焦点距離・主点など | 3次元座標の計算 |

通常のカメラ画像では、画素ごとに色の情報が記録されます。

一方、深度データでは、それぞれの画素に対応する距離が記録されます。

例えば、以下のようなイメージ

<b>深度データ</b>

```txt
単位：m

┌─────────────────┐
│ 3.2  3.1   3.0  │
│ 3.1  2.8   2.9  │
│ 2.8  1.4   1.5. │ ← 枝まで約1.5m
│ 3.0  2.7   2.8. │
└─────────────────┘
```

深度データを利用することで、障害物がカメラからどれくらい離れているかを推定できます。

ただし、<b>深度データを取得するだけでは、その物体が利用者の頭や胸の高さにあるかは分かりません。</b>

そのため、次のCore Motionと組み合わせる必要があります。

### 2-2. Core Motion：iPhoneの傾きを取得

Core Motionは、iPhoneに搭載された加速度センサーやジャイロセンサーなどの情報を利用できるフレームワークです。

今回のシステムでは、特に以下の情報を使用します。

- 重力方向
- iPhoneの傾き
- iPhoneの姿勢

Appleの<code>CMDeviceMotion</code>では、重力ベクトルや端末の姿勢を取得できます。[Apple Developer](https://developer.apple.com/la/documentation/coremotion/cmdevicemotion/gravity?utm_source=chatgpt.com)

#### なぜ傾きが重要なのか？

今回はiPhoneを首から掛けるため、常に一定の姿勢になるとは限りません。

iPhoneの角度が変わると、同じ画像上の位置に映っている物体でも、実際の高さが変化します。

傾きを考慮しないと、地面にある障害物を胸の高さにあると誤判定する可能性があります。

そこでCore Motionの重力ベクトルを利用し、カメラ座標系の情報を重力方向に基づく座標系へ変換します。

ただし、傾きが分かっても、iPhoneが地面から何mの高さにあるかは分かりません。

そのため、<b>装着時のカメラ高さを設定・推定する仕組みも必要</b>です。

さらに首掛け方式では、歩行による揺れや横方向への回転も発生します。重力方向だけでは進行方向を特定できないため、進路をどのように推定するかも設計上の重要な課題です。

---

### 2-3. HeadLevelGeometry：胸・頭の高さの障害物を判定

ここが障害物検知システムの中心です。

<code>HeadLevelGeometry</code>は、提示された構成における既存の幾何判定処理です。

具体的には、AVFoundationとCore Motionから得られる情報を利用して、障害物の3次元位置を求め、危険性を判定します。

なお、<code>HeadLevelGeometry</code>はApple標準のフレームワーク名ではなく、既存アプリ側の実装を指しているものとして説明します。実際の処理内容は、そのコードを確認する必要があります。

#### STEP 1：画素を3次元座標に変換

カメラから取得した情報を使い、画像上の点を3次元座標に変換します。

一般的なピンホールカメラモデルでは、

\\\[<br />X=\\frac\{(u-c\_x)Z\}\{f\_x\}<br />\\\]\\\[<br />Y=\\frac\{(v-c\_y)Z\}\{f\_y\}<br />\\\]\\\[<br />Z=d<br />\\\]

となります。

| 記号 | 意味 |
| --- | --- |
| \\(u,v\\) | 画像上の画素座標 |
| \\(c\_x,c\_y\\) | カメラの主点 |
| \\(f\_x,f\_y\\) | 焦点距離（画素単位） |
| \\(d\\) | 深度値 |
| \\(X,Y,Z\\) | カメラ座標系の3次元位置 |

ここでは、深度値がカメラの光軸方向の距離であることを仮定しています。

#### STEP 2：重力方向を使って高さを推定

次に、Core Motionで取得した重力ベクトルを利用します。

カメラ座標系から端末座標系への変換を考慮したうえで、鉛直方向の位置を計算します。

例えば、カメラが地面から1.2mの位置にある場合、

- カメラより0.4m上にある物体：高さ1.6m
- カメラと同じ高さにある物体：高さ1.2m
- カメラより0.5m下にある物体：高さ0.7m

と推定できます。

#### STEP 3：危険な高さにあるか判定

例えば、試作段階で検出対象の高さを以下のように設定します。

| 高さ | 判定 |
| --- | --- |
| 0〜0.8m | 検知対象外 |
| 0.8〜1.2m | 胸付近の障害物候補 |
| 1.2〜1.8m | 胸・頭付近の障害物候補 |
| 1.8m以上 | 条件に応じて判定 |

※これらはアルゴリズムを説明するための仮の値です。実際には利用者の身長、体格、装着位置などに応じて調整が必要です。

特に重要なのは、物体の高さだけではなく、<b>利用者の身体が通過する空間と障害物が重なっているか</b>を判定することです。

例えば、頭上にある枝でも、進路から横に1m離れていれば衝突しない可能性があります。

そのため、少なくとも以下の3要素を組み合わせます。

1. 障害物までの距離
2. 障害物の高さ
3. 進行方向に対する障害物の位置

#### 判定例

```txt
障害物A
  距離：1.0m
  高さ：1.6m
  進行方向：正面

  → 危険


障害物B
  距離：2.5m
  高さ：1.5m
  進行方向：正面

  → 注意


障害物C
  距離：0.8m
  高さ：1.5m
  進行方向：右側1.5m

  → 進路外なら検出なし
```

ここまでが既存の<code>HeadLevelGeometry</code>で実現したい機能です。

## 3. 状態生成処理：検出結果を4つの状態に変換する

HeadLevelGeometryで障害物を判定した後、その結果を白杖側に通知しやすい形式に変換します。

今回追加するのが、この<b>状態生成処理</b>です。

障害物までの距離をそのままESP32C3に送る方法もありますが、今回は推奨しません。

理由は、ESP32C3側に距離から危険度を判定する処理まで実装する必要が生じるからです。

iPhone側で危険度を決定し、ESP32C3には最終的な状態だけを送信する方が、役割が明確になります。

### 3-1. 4つの状態

| 状態 | 意味 | 白杖側の動作 |
| --- | --- | --- |
| 検出なし | 判定範囲内に障害物が検出されていない | 振動なし |
| 注意 | 接近に注意が必要な障害物がある | 断続的に振動 |
| 危険 | 衝突する可能性が高い障害物がある | 強い・短い間隔の振動 |
| 検知不能 | センサーや処理の問題で安全性を判定できない | 専用の異常通知パターン |

ここで特に重要なのが「検出なし」と「検知不能」の違いです。

<b>検出なし</b>

正常に検知処理が動作しており、設定した検出範囲内に障害物が見つかっていない状態です。

ただし、周囲全体の安全が保証されたわけではありません。

<b>検知不能</b>

例えば、以下の状況です。

- カメラの映像を取得できない
- 深度データが取得できない
- 深度データが古い
- センサーの有効範囲外
- iPhoneが大きく揺れている
- iPhoneが想定外の方向を向いている
- 障害物判定処理が停止している

このような場合、「障害物を検出していない」と扱ってはいけません。

検出処理自体が成立していないためです。

### 3-2. 状態判定の具体例

初期試作では、次のような判定を考えられます。

| 条件 | 状態 |
| --- | --- |
| 深度データなどが無効 | 検知不能 |
| 障害物まで0.8m未満 | 危険 |
| 障害物まで0.8〜2.0m | 注意 |
| 有効な検出範囲に障害物なし | 検出なし |

※0.8mと2.0mは説明用の仮設定です。

実際には歩行速度、システム遅延、停止に必要な距離を考慮して設定します。

また、境界付近で障害物までの距離が変化すると、注意と危険が短時間で頻繁に切り替わる可能性があります。

そのため、ヒステリシスや時間的な平滑化を導入することが望ましいです。

例えば、危険状態への移行は素早く行い、危険状態から注意状態への復帰は一定時間確認してから行う設計が考えられます。

## 4. Core Bluetooth：iPhoneから白杖へ状態を送信

次に、iPhoneで決定した危険状態を白杖側へ送信します。

ここでは、\*\*Bluetooth Low Energy（BLE）\*\*を使用します。

### 4-1. BLEとは？

BLEは、Bluetoothの中でも低消費電力で小さなデータをやり取りすることに適した通信方式です。

今回のシステムでは、画像や深度データそのものを送信する必要はありません。

必要なのは、例えば次のような情報だけです。

```txt
現在の状態：危険
```

つまり、送信データが非常に小さいため、BLEが適しています。

また、iPhoneとESP32C3の間で直接通信できるため、インターネット接続も不要です。

### 4-2. CentralとPeripheral

BLEでは、一般に以下の2つの役割を設定します。

| 役割 | デバイス | 処理 |
| --- | --- | --- |
| Central | iPhone | BLE機器を検索して接続する |
| Peripheral | ESP32C3 | 接続を受け付け、データを受信する |

今回の構成では、iPhoneがCentral、ESP32C3がPeripheralになります。

通信の流れは次のとおりです。

```txt
【iPhone】                  【ESP32C3】

BLE機器を検索
     │
     ├──── Scan ────────────→ BLE広告を送信
     │
対象機器を発見
     │
     ├──── Connect ────────→ 接続を受け付け
     │
GATTサービスを探索
     │
     ├──── Discover ───────→ サービス情報を返す
     │
Characteristicを取得
     │
     ├──── Write ──────────→ 状態を受信
     │                          │
     │                          ▼
     │                      振動制御
     │
     ├──── Write ──────────→ 次の状態を受信
     │                          │
     │                          ▼
     │                      振動制御を更新
```

### 4-3. BLE GATTとは？

GATT（Generic Attribute Profile）は、BLE機器間でデータをやり取りするための仕組みです。

GATTでは、データを主に次の階層で管理します。

```txt
ESP32C3
  │
  └─ GATT Server
       │
       └─ Service
            │
            ├─ State Characteristic
            │     └─ 危険状態を受信
            │
            └─ Status Characteristic
                  └─ デバイス状態を通知
```

例えば、今回のシステム専用のGATTサービスを定義します。

| 項目 | 用途 |
| --- | --- |
| Service UUID | 白杖振動デバイスの識別 |
| State Characteristic | iPhoneから危険状態を送信 |
| Status Characteristic | ESP32C3から接続・電池などの状態を通知 |

UUIDは独自に生成した128bit UUIDを使用できます。

### 4-4. 送信するデータ形式

初期実装では、危険状態を1バイトの整数で表現できます。

| 送信値 | 状態 |
| --- | --- |
| <code>0x00</code> | 検出なし |
| <code>0x01</code> | 注意 |
| <code>0x02</code> | 危険 |
| <code>0x03</code> | 検知不能 |

例えば、iPhoneが危険と判定した場合、

```txt
iPhone
  │
  │ 0x02
  ▼
ESP32C3
  │
  │ 危険状態として解釈
  ▼
振動モーター
  │
  └─ 危険用の振動パターン
```

となります。

この方式なら、ESP32C3側では1バイトのデータを読み取るだけで状態を識別できます。

ただし、実用上は状態だけでなく、<b>シーケンス番号や通信データの有効期限を管理すること</b>を推奨します。

例えば、以下のような4バイトのメッセージが考えられます。

| バイト位置 | 内容 | 例 |
| --- | --- | --- |
| 0 | プロトコルバージョン | <code>0x01</code> |
| 1 | 危険状態 | <code>0x02</code> |
| 2 | シーケンス番号 | <code>0x15</code> |
| 3 | 予約領域 | <code>0x00</code> |

送信例：

```txt
01 02 15 00
```

意味は、

```txt
バージョン：1
状態：危険
シーケンス番号：21
予約領域：0
```

です。

シーケンス番号は、最新のデータを管理するために使用します。

なお、データの有効期限は受信側のタイマーで管理すればよいため、必ずしもメッセージ内に時刻を含める必要はありません。

## 5. XIAO ESP32C3：BLE受信と振動制御

### 5-1. XIAO ESP32C3とは？

XIAO ESP32C3は、Seeed Studioが提供する小型マイコンボードです。

ESP32-C3を搭載しており、Bluetooth Low EnergyやWi-Fiを利用できます。

今回のシステムでは、Wi-Fiは使用せず、BLE通信とGPIO制御を利用します。

公式資料によると、XIAO ESP32C3のD1端子はGPIO3に対応しています。[Seeed Studio](https://wiki.seeedstudio.com/XIAO_ESP32C3_Getting_Started/?utm_source=chatgpt.com)

主な役割は以下の4つです。

1. iPhoneからBLEで危険状態を受信する
2. 通信データが有効か確認する
3. 受信状態に対応する振動パターンを生成する
4. GPIOを通じてモータードライバを制御する

### 5-2. なぜiPhoneで直接モーターを制御しないのか？

iPhone側で振動のON/OFFまで決定し、その都度BLEで送信することも理論上は可能です。

例えば、

```txt
iPhone → ON送信
100ms後
iPhone → OFF送信
100ms後
iPhone → ON送信
```

といった方式です。

しかし、この方式では通信遅延の影響を受けます。

例えば、OFF命令の到着が遅れると、想定より長い時間モーターが振動する可能性があります。

そのため、<b>iPhoneは危険状態だけを送り、振動の時間制御はESP32C3側で実行する</b>方式が適しています。

```txt
iPhone
  │
  │ 「危険」
  ▼
ESP32C3
  │
  ├─ 150ms ON
  ├─ 100ms OFF
  ├─ 150ms ON
  └─ 100ms OFF
```

これなら、接続中の通信タイミングが多少変動しても、ESP32C3側で一貫した振動パターンを生成できます。

### 5-3. データ有効期限の確認

この機能は、安全性の観点から非常に重要です。

例えば、障害物を検出していない状態で、通信が停止した場合を考えます。

```txt
時刻        受信状態

0.0秒       検出なし
0.1秒       検出なし
0.2秒       検出なし
0.3秒       通信停止
0.4秒       受信なし
0.5秒       受信なし
0.6秒       受信なし
```

このとき、ESP32C3が最後の「検出なし」を保持し続けると、システムが動作していないにもかかわらず、振動が発生しない状態になります。

そこで、受信データに有効期限を設けます。

例えば、以下のように設定します。

```txt
BLE受信間隔：100ms
データ有効期限：500ms
```

最後の正常な状態メッセージを受信してから500msを超えた場合、ESP32C3は通常の障害物判定状態を破棄し、通信異常状態に遷移します。

```txt
正常受信
  │
  ▼
受信時刻を保存
  │
  ▼
現在時刻 − 最終受信時刻
  │
  ├─ 500ms以内
  │     └─ 受信した状態を採用
  │
  └─ 500ms超過
        └─ 通信異常パターンに変更
```

500msは試作時の初期値であり、通信間隔や遅延測定に基づいて調整する必要があります。

また、「BLE接続が維持されていること」と「有効な検出結果を受信できていること」は別です。

そのため、接続状態だけでなく、<b>最後に有効なメッセージを受信した時刻</b>を監視します。

通信異常時には、危険状態とは区別できる専用の振動パターンを出す設計が望ましいです。

## 6. GPIO3（D1）：モーター制御信号を出力

ESP32C3は、受信した状態に応じてGPIOの出力を切り替えます。

GPIOは、マイコンから外部機器へ電気信号を出力したり、外部機器から信号を入力したりするための端子です。

今回使用する端子は、

<b>XIAO ESP32C3のD1（GPIO3）</b>

です。

### 6-1. HIGHとLOW

GPIOを出力モードに設定すると、基本的に2つの状態を切り替えられます。

| GPIO状態 | 電圧の目安 | 意味 |
| --- | --- | --- |
| HIGH | 約3.3V | ON信号 |
| LOW | 約0V | OFF信号 |

例えば、Arduino環境では以下のように制御できます。

```txt
const int MOTOR_PIN = D1;

void setup() {
    pinMode(MOTOR_PIN, OUTPUT);
    digitalWrite(MOTOR_PIN, LOW);
}

void loop() {
    digitalWrite(MOTOR_PIN, HIGH);
    delay(200);

    digitalWrite(MOTOR_PIN, LOW);
    delay(200);
}
```

これはGPIOを200msごとにHIGHとLOWへ切り替える基本的な例です。

ただし、このコードだけでは振動モーターを直接駆動できません。

### 6-2. なぜGPIOから直接モーターに接続しないのか？

理由は、モーターを動作させるための電流が、GPIOで安全に供給できる電流を超える可能性があるからです。

特にモーターの起動時には、定常動作時より大きな電流が流れる場合があります。

GPIOに直接モーターを接続すると、マイコンの動作不良や破損につながるおそれがあります。

そこで、GPIOは制御信号だけを出力し、モーターへの電力供給にはドライバ回路を使用します。

```txt
ESP32C3
   │
   │ GPIO3
   │ HIGH / LOW
   │
   ▼
DRV8835
   │
   │ モーター駆動電流
   │
   ▼
振動モーター
```

<b>GPIOはモーターの電源ではなく、モーターを動かすための指令を出す端子</b>と考えると分かりやすいです。

---

## 7. DRV8835：モーターを駆動する

### 7-1. DRV8835とは？

DRV8835は、Texas Instrumentsが提供するモータードライバICです。

DCモーターを駆動するためのHブリッジ回路を内蔵しています。

ESP32C3からの制御信号に従って、モーターに電力を供給できます。

DRV8835には、主に以下の2種類の制御モードがあります。

| モード | 概要 |
| --- | --- |
| IN/IN | 2つの入力でモーターの動作を制御 |
| PHASE/ENABLE | 回転方向と駆動の有効・無効を制御 |

今回のように単純な振動モーターを使用する場合は、<b>IN/INモードで片方の入力をLOWに固定し、もう片方をGPIOで制御する方式</b>が分かりやすいです。

DRV8835の公式データシートでも、IN/INモードでは入力の組み合わせに応じてモーターの駆動・停止を制御できることが示されています。[Texas Instruments](https://www.ti.com/jp/lit/gpn/DRV8835?utm_source=chatgpt.com)

### 7-2. 具体的な配線

以下は、DRV8835を搭載したモータードライバ基板を使用する場合の概念的な配線例です。

```txt
        XIAO ESP32C3
       ┌─────────────┐
       │             │
       │ D1 / GPIO3  ├──────────┐
       │             │          │
       │ GND         ├──────┐   │
       │             │      │   │
       └─────────────┘      │   │
                            │   │
                            ▼   ▼
                      ┌────────────┐
                      │  DRV8835   │
                      │            │
                      │  GND  AIN1 │
                      │       AIN2 │← LOW固定
                      │            │
                      │ AOUT1 AOUT2│
                      └──┬────┬────┘
                         │    │
                         ▼    ▼
                      ┌──────────┐
                      │ 振動     │
                      │ モーター │
                      └──────────┘
```

実際には、これに加えてDRV8835のモーター電源、ロジック電源、MODE端子、スリープ端子などを適切に接続する必要があります。

基板によって端子名や必要な外部配線が異なるため、使用するモータードライバ基板の型番を確認して配線を確定します。

IN/INモードでは、例えば次のように動作します。

| AIN1 | AIN2 | 動作 |
| --- | --- | --- |
| LOW | LOW | モーター停止（コースト） |
| HIGH | LOW | モーター駆動 |
| LOW | HIGH | 逆方向に駆動 |
| HIGH | HIGH | ブレーキ |

今回のコイン型振動モーターでは逆回転を利用する必要はないため、AIN2をLOWに固定する設計が可能です。

ただし、DRV8835の電源電圧がモーターの定格電圧に適合していること、起動電流が許容範囲内にあることを確認する必要があります。

### 7-3. 振動の強さも変更できる？

可能です。

HIGH/LOWを切り替えるだけなら、モーターのON/OFF制御になります。

一方、PWM（Pulse Width Modulation）を利用すると、振動の強さをある程度調整できます。

PWMとは、短い周期でONとOFFを繰り返し、ONになっている時間の割合を変える制御方法です。

例えば、

```txt
Duty 25%

ON  OFF OFF OFF
■■  □□  □□  □□


Duty 50%

ON  ON  OFF OFF
■■  ■■  □□  □□


Duty 100%

ON  ON  ON  ON
■■  ■■  ■■  ■■
```

となります。

一般にデューティ比を上げると、モーターへ供給される平均的な電力が増えます。

ただし、モーターの振動強度とデューティ比は必ずしも比例しません。

また、デューティ比が小さすぎるとモーターが起動しない場合もあります。

そのため、初期試作では振動の強さを複雑に変更するよりも、<b>振動時間と振動間隔で危険状態を区別する方式</b>から始めるのがよいです。

## 8. コイン型振動モーター：利用者への通知

### 8-1. コイン型振動モーターとは？

コイン型振動モーターは、薄い円盤状の小型モーターです。

スマートフォンや小型電子機器の振動通知に利用されるタイプがあります。

今回のシステムでは、このモーターを白杖のグリップカバー内部に設置します。

```txt
        白杖グリップ

      ┌────────────┐
      │            │
      │  振動      │
      │  モーター  │
      │   ◎        │
      │            │
      │  制御回路  │
      │            │
      └─────┬──────┘
            │
            │
            │ 白杖
            │
            │
```

利用者は白杖を握った状態で、グリップに伝わる振動を感じ取ります。

### 8-2. なぜグリップ部分に配置するのか？

主な理由は3つです。

<b>① 振動を手に直接伝えられる</b>

白杖を握る手に振動を伝えられるため、スマートフォンの画面や音声に依存しません。

<b>② 聴覚を妨げにくい</b>

視覚障害者の歩行では、周囲の音も重要な情報源になります。

振動通知なら、警告音を常時出す必要がありません。

<b>③ 通知用機器を別に持つ必要がない</b>

白杖と通知装置を一体化することで、利用時の負担を抑えられます。

ただし、グリップにモーターを取り付けると、白杖を地面に接触させた際の感触を妨げる可能性があります。

そのため、モーターの位置、固定方法、振動強度は慎重に調整する必要があります。

## 9. 危険状態と振動パターンの対応

今回の設計では、4つの状態を異なる振動パターンで表現します。

以下は初期試作用の例です。

| 状態 | 振動パターン | 意図 |
| --- | --- | --- |
| 検出なし | 振動なし | 不要な通知を抑える |
| 注意 | 150ms振動 → 850ms停止 | 障害物への接近を知らせる |
| 危険 | 200ms振動 → 100ms停止 | 強い注意を促す |
| 検知不能 | 100ms振動を3回 → 長めに停止 | システム状態の異常を知らせる |

振動を時間軸で表すと、以下のようになります。

<b>検出なし</b>

```txt
時間 →
____________________________

振動なし
```

<b>注意</b>

```txt
時間 →

■■■_________________
■■■_________________

低頻度の振動
```

<b>危険</b>

```txt
時間 →

■■■■__■■■■__■■■■__■■■■__

短い間隔で繰り返す
```

<b>検知不能</b>

```txt
時間 →

■■_■■_■■______________
■■_■■_■■______________

3回振動して長めに停止
```

これらは設計例であり、振動パターンの識別しやすさが検証済みという意味ではありません。

実用化を想定する場合、少なくとも「注意」「危険」「検知不能」の3種類を確実に区別できるか、実際の利用者を対象に検証する必要があります。

また、「検知不能」は障害物の危険とは性質が異なるため、通常の警告とは明確に区別できるパターンにすることが重要です。

## 10. 電源構成：白杖側はどのように動作させる？

白杖側の装置は、iPhoneと物理的に接続しないため、独立した電源が必要です。

試作段階では、3.7Vのリチウムポリマーバッテリーを利用する構成が考えられます。

XIAO ESP32C3は3.7Vリチウムバッテリーからの給電に対応しています。[Seeed Studio](https://wiki.seeedstudio.com/XIAO_ESP32C3_Getting_Started/?utm_source=chatgpt.com)

### 電源と信号の構成

```txt
       3.7Vバッテリー
              │
       ┌──────┴──────┐
       │             │
       ▼             ▼
   XIAO ESP32C3   モーター用電源回路
       │             │
       │             ▼
       │          DRV8835
       │             │
       │ GPIO3       │
       └─────────────┤
                     │
                     ▼
                振動モーター
```

ここで注意したいのが、<b>ESP32C3と振動モーターの動作電圧が必ずしも同じではないこと</b>です。

例えば、次のような組み合わせが考えられます。

| 部品 | 電源 |
| --- | --- |
| XIAO ESP32C3 | 3.7Vバッテリー |
| DRV8835 | モーターに適合する電源 |
| コイン型モーター | 製品ごとの定格電圧 |

3V定格のモーターに満充電時約4.2Vとなるリチウムイオン電池を直接接続すると、定格を超える可能性があります。

そのため、モーターの仕様に応じて電圧調整回路などを検討します。

また、実際に白杖へ装着する場合は、バッテリーの保護回路、配線の絶縁、防滴対策、充電方法も考慮する必要があります。

## 11. ソフトウェアの実装構成

このシステムでは、iPhoneアプリとESP32C3のファームウェアをそれぞれ開発します。

### 11-1. iPhone側：Swift

既存のHeadLevelGeometryを利用する場合、以下のような構成が考えられます。

```txt
iOS Application
│
├─ CameraManager.swift
│    └─ AVFoundationによる深度取得
│
├─ MotionManager.swift
│    └─ Core Motionによる姿勢取得
│
├─ HeadLevelGeometry.swift
│    └─ 障害物の3次元位置・高さ判定
│
├─ HazardStateManager.swift【追加】
│    └─ 検出なし・注意・危険・検知不能
│
├─ BLEManager.swift【追加】
│    └─ ESP32C3とのBLE通信
│
└─ ContentView.swift
     └─ 接続状態や検知状態の表示
```

既存のHeadLevelGeometryが機能しているのであれば、基本的には<code>HazardStateManager</code>と<code>BLEManager</code>の追加が中心となります。

#### HazardStateManagerの例

以下はSwiftで状態を表現する例です。

```txt
enum HazardState: UInt8 {
    case clear = 0
    case caution = 1
    case danger = 2
    case unavailable = 3
}
```

次に、HeadLevelGeometryから取得した結果を状態に変換します。

```txt
func determineHazardState(
    distance: Float?,
    isDetectionValid: Bool
) -> HazardState {

    guard isDetectionValid else {
        return .unavailable
    }

    guard let distance = distance,
          distance.isFinite,
          distance >= 0 else {
        return .clear
    }

    if distance < 0.8 {
        return .danger
    }

    if distance < 2.0 {
        return .caution
    }

    return .clear
}
```

ここでの<code>distance</code>は、単なる画面内の最短距離ではなく、<b>HeadLevelGeometryが進路上かつ対象高さにあると判定した障害物までの距離</b>を想定しています。

また、このサンプルコードでは障害物が存在しない場合に<code>nil</code>を使用しています。

実際には「障害物が存在しない」と「距離を計算できない」を明確に分ける必要があります。距離の計算に失敗した場合は、原則として検知不能へ遷移させる設計にしてください。

### 11-2. BLEManagerの例

Core Bluetoothを使用して、ESP32C3へ状態を送信します。

```txt
import CoreBluetooth

final class BLEManager: NSObject {

    private var peripheral: CBPeripheral?

    private var stateCharacteristic: CBCharacteristic?

    func sendState(_ state: HazardState) {

        guard let peripheral,
              let characteristic = stateCharacteristic
        else {
            return
        }

        let data = Data([state.rawValue])

        peripheral.writeValue(
            data,
            for: characteristic,
            type: .withResponse
        )
    }
}
```

このコードは状態送信部分だけを示した簡略例です。

実際には、Central Managerの生成、デバイスの検索、接続、GATTサービスの探索、Characteristicの取得などを追加します。

送信方法は<code>.withResponse</code>を使用する例にしていますが、応答があることだけで障害物検知や振動の実行まで保証されるわけではありません。

実運用では、ESP32C3側からの状態通知やタイムアウト監視も組み合わせることを推奨します。

### 11-3. ESP32C3側：Arduino C++

ESP32C3側は、Arduino IDEまたはPlatformIOを使用して開発できます。

基本的な構成は以下のようになります。

```txt
ESP32C3 Firmware
│
├─ BLE通信処理
│    └─ iPhoneから状態を受信
│
├─ 通信監視処理
│    └─ 最終受信時刻を管理
│
├─ 状態管理処理
│    └─ 危険状態と通信異常を管理
│
└─ モーター制御処理
     └─ GPIO3をHIGH/LOW
```

例えば、振動を制御する関数は次のように作成できます。

```txt
#define MOTOR_PIN D1

enum HazardState {
    CLEAR = 0,
    CAUTION = 1,
    DANGER = 2,
    UNAVAILABLE = 3
};

void setup() {
    pinMode(MOTOR_PIN, OUTPUT);
    digitalWrite(MOTOR_PIN, LOW);
}

void motorOn() {
    digitalWrite(MOTOR_PIN, HIGH);
}

void motorOff() {
    digitalWrite(MOTOR_PIN, LOW);
}
```

BLEで受信した状態を使って、振動パターンを切り替えます。

ただし、最終的な実装では<code>delay()</code>を多用しないことが重要です。

長い<code>delay()</code>で処理を停止させると、新しい危険状態の反映が遅れる可能性があります。

そのため、<code>millis()</code>を利用して、BLE受信処理を妨げずに振動のON/OFFを切り替える方式が適しています。

## 12. 実装する際の重要な課題

このシステムは技術的に実装可能な構成ですが、歩行支援として使用する場合には、いくつか重要な課題があります。

### ① iPhoneの画面を身体側に向けること

首掛け方式では、背面カメラが前方を向くようにiPhoneを装着します。

ただし、<b>画面が身体側を向いていることと、カメラが常に使用できることは別問題</b>です。

Appleの通常のAVFoundationカメラキャプチャは、アプリがバックグラウンドへ移行すると中断される制約があります。[Apple Developer](https://developer.apple.com/documentation/avfoundation/avcapturesession/interruptionreason/videodevicenotavailableinbackground?changes=_2&utm_source=chatgpt.com)

したがって、画面を消してバックグラウンド状態のまま検知を続ける設計は、そのままでは成立しません。

初期試作では、アプリをフォアグラウンドで実行し、画面を身体側に向けた状態で動作を確認する構成が現実的です。

### ② 首掛けiPhoneの揺れ

歩行時にはiPhoneが前後左右に揺れます。

この揺れによって、次の問題が発生します。

- 深度データの取得方向が変わる
- 進行方向とカメラの向きが一致しなくなる
- 高さ判定が不安定になる
- 障害物が一時的に画角から外れる

Core Motionは姿勢補正に役立ちますが、それだけですべての問題を解決できるわけではありません。

特に、カメラが進行方向から外れている場合は、進路上の障害物を見落とす可能性があります。

そのため、首掛け部分の固定方法や、進行方向からのずれを検知する仕組みも検討する必要があります。

### ③ 深度センサーの限界

LiDARによる深度取得は、すべての材質・距離・環境で正確に動作するわけではありません。

例えば、以下のような条件では注意が必要です。

- 細い枝やワイヤー
- ガラスなどの透明な物体
- 反射特性の特殊な物体
- センサーの測距範囲外
- 深度データが欠損する領域

特に、今回検知したい木の枝などは、細い形状であることが問題になります。

深度センサーが障害物を十分に捉えられなければ、幾何判定が正しくても検出できません。

### ④ BLEの通信遅延

BLEは比較的低遅延な通信が可能ですが、遅延時間が常に一定というわけではありません。

そのため、障害物の検出から利用者に振動が伝わるまでの時間を測定する必要があります。

システム全体の遅延は、概念的には以下のように表せます。

\\\[<br />T\_\{\\mathrm\{total\}\}<br />=<br />T\_\{\\mathrm\{sensor\}\}<br />+<br />T\_\{\\mathrm\{processing\}\}<br />+<br />T\_\{\\mathrm\{BLE\}\}<br />+<br />T\_\{\\mathrm\{motor\}\}<br />\\\]

| 項目 | 内容 |
| --- | --- |
| \\(T\_\{\\mathrm\{sensor\}\}\\) | 深度データを取得するまでの時間 |
| \\(T\_\{\\mathrm\{processing\}\}\\) | 障害物と危険度を判定する時間 |
| \\(T\_\{\\mathrm\{BLE\}\}\\) | ESP32C3まで状態が届く時間 |
| \\(T\_\{\\mathrm\{motor\}\}\\) | モーターが実際に振動するまでの時間 |

これに加えて、利用者が振動に気づいて反応するまでの時間も考慮する必要があります。

例えば、歩行速度が1.2m/s、システム全体の遅延が0.3秒であれば、警告が発生するまでに利用者は約0.36m進みます。

危険判定の距離は、このような遅延を考慮して決める必要があります。

### ⑤ 振動が確実に伝わるか

白杖のグリップ内部にモーターを設置しても、必ずしも利用者が振動を明確に感じられるとは限りません。

振動の伝達には以下の要素が影響します。

- モーターの振動強度
- グリップカバーの材質
- モーターの取り付け位置
- 白杖の握り方
- 歩行中の手の動き

また、振動モーターにはERM型やLRA型などがあります。

一般的なコイン型ERMモーターであればDRV8835を利用する構成が考えられますが、LRA型の場合は専用のハプティックドライバを使用した方が適している場合があります。

したがって、使用するモーターの種類も事前に決めておく必要があります。

## 13. 実装する順番

既存のHeadLevelGeometryが動作している前提であれば、以下の順番が効率的です。

| 段階 | 実装内容 | 確認すること |
| --- | --- | --- |
| STEP 1 | ESP32C3単体でGPIO制御 | モーターをON/OFFできる |
| STEP 2 | DRV8835と振動モーターを接続 | 安定して振動する |
| STEP 3 | ESP32C3にBLE GATT Serverを実装 | iPhoneから接続できる |
| STEP 4 | iPhoneにBLEManagerを追加 | 状態データを送信できる |
| STEP 5 | ESP32C3に振動パターンを実装 | 4状態を区別できる |
| STEP 6 | HeadLevelGeometryと連携 | 障害物検知に応じて振動する |
| STEP 7 | タイムアウト・通信切断処理 | 異常を通知できる |
| STEP 8 | 白杖のグリップへ組み込み | 握りながら振動を確認できる |

最初から白杖にすべての部品を組み込む必要はありません。

まずは机上でESP32C3、DRV8835、振動モーターを配線し、iPhoneからBLEで振動を制御できるところまで完成させるのがよいです。

その後、既存の障害物検知処理と連携させます。

実際の歩行試験に進む際は、誘導者や安全管理者がいる環境で実施し、本システムを白杖の代替や唯一の安全確認手段として使用しないことが前提です。

### 結論

<b>今回のシステム構成は、既存のiPhone障害物検知アプリに振動通知機能を追加する方法として妥当です。</b>

特に、以下の役割分担が適しています。

- <b>iPhone：</b> センサー情報の取得、障害物検出、危険度判定
- <b>BLE：</b> 危険状態を小さなデータとして送信
- <b>ESP32C3：</b> 受信状態の管理、振動パターン生成、通信監視
- <b>DRV8835：</b> 振動モーターへの電力供給制御
- <b>白杖グリップ：</b> 利用者への触覚通知

ただし、開発上の最も重要な課題は、BLE通信やモーター制御ではありません。

<b>① 首掛け状態でも障害物を安定して検出できるか、② 危険を十分早く通知できるか、③ 検知不能時に利用者がシステム異常を認識できるか</b>の3点です。

また、研究として取り組むのであれば、単に障害物を振動で通知するだけでなく、首掛けによる姿勢変動に対する検出精度、危険度に応じた振動パターンの認識率、システム全体の応答遅延などを定量的に評価することで、研究上の意義を検討できます。

なお、現段階では<b>既存のHeadLevelGeometryがどのような条件で障害物を検出・判定しているかが未確認</b>です。そのため、まず既存コードの入力・出力と「検出なし」「検知不能」の区別方法を確認することが、具体的な実装設計の出発点になります。
