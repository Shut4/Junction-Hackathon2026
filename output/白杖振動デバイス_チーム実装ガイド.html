配線表・電圧調整・GPIO設定

設定と動作

  • AE-TPS63802：VR1を必ず実装し、XIAO未接続でVOUTを5.00Vに調整する。EN(CN1-4)は基板内でVINへプルアップ済みなので未接続。CP1(PG)も未接続。JP1は短絡してパワーセーブモードとする案。負荷過渡時の電圧を実機確認する。
  • AE-DRV8835-P：MODEをGNDにしてIN/INモード。J1ジャンパーで設定する場合もLOW側。VCC側へ短絡する設定と併用しない。
  • IN2は常にLOW。IN1 HIGHでOUT1=H/OUT2=Lとなり振動、IN1 LOWで両出力Hi-Zとなり停止。
  • LBV10B-009は駆動回路内蔵のブラシレスモーターで極性がある。逆転・ブレーキ設定は使わない。初回は秒単位のON/OFFで確認し、高周波PWMは採用しない。
  • IN1/IN2/MODEにはドライバーIC内のプルダウンがある。起動直後のソフトウェアでもD1出力をLOWへ初期化する。
  • 電池はモーターへ公称3Vを供給する。新品時の電圧上振れ、電圧低下時の起動・振動・BLE切断を実機確認する。昇圧回路の動作下限とモーターの実用下限は異なる。
  • 1S4は昇圧回路側をA、XIAO側をK（帯側）にする。USBから外部電源系への逆流を防ぐ経路。USB接続中はSW1を切ってもXIAOは動作する。電池を充電する回路ではない。
  • 電池保持部・回路基板が既存グリップに収まることは未確認。収納設計は白杖の実測後に行う。

確認手順

  1. 無通電でGND共通、電源極性、電源とGND間の短絡がないことを確認。
  2. U1のVR1実装と出力5.00Vを無負荷で確認。
  3. 電源OFFでXIAOを接続。起動と3V3出力を確認。
  4. ドライバーを接続し、IN1 LOWで停止、HIGHで正しい極性の振動が得られるか短時間確認。
  5. BLE接続・切断、繰り返し振動時の電源電圧と平均電流を測定。
回路の要点

全体回路図 / 拡大用SVG / 詳細接続表

単3アルカリ2本（公称3V）→ スイッチ → VBAT
  ├─ TPS63802（5V設定）→ 1S4 → XIAO 5V
  └─ DRV8835 VM → OUT1/OUT2 → モーター
XIAO 3V3 → DRV8835 VCC
XIAO D1 / GPIO3 → DRV8835 IN1
DRV8835 IN2・MODE → GND
全てのGND → 電池－
  • D1という名前は「XIAOのD1端子」と「回路図のダイオードD1」の2か所で使われる。配線時は部品名と端子名を区別。
  • TPS63802のVR1を必ず取り付け、XIAO未接続で5.00Vに調整。ENは基板内プルアップにより未接続。JP1短絡で省電力とする案。
  • 1S4の帯なし側(A)を電源出力、帯側(K)をXIAO 5Vへ。電圧降下後の基板入力を確認。
  • DRV8835-PはIN/INモード。IN2=LOW固定、MODE=LOW、IN1=HIGHでOUT1=H/OUT2=L、IN1=LOWでHi-Z。
  • LBV10B-009はブラシレス駆動回路内蔵・極性あり。逆転しない。初期版は秒単位ON/OFF。一般のブラシ付きモーター向けPWMをそのまま適用しない。
  • USBデバッグ中は電池スイッチを切ってもXIAOはUSBで動く。電池が充電される回路ではない。
  • モーターと無線送受信の負荷で電源が落ちないか測定。低電圧時の状態は未検証。ソフトウェアの電池監視は現状ない。

電池持ちの考え方・測定する値

現時点では測定値なし。単3×2本なら容量mAhは2倍にならず、直列で電圧が加算される。アルカリ電池の容量は負荷・終止電圧・温度で変わる。

以前の平均電流29.3mAは「50mAで5ms、27mAで45ms」という仮定の時間平均。通信間隔・実際の電流・給電測定点を確定した値ではなく、電池寿命の保証に使わない。

D/Cが測る項目：電池側の平均電流とピーク、電池電圧、昇圧後5V、XIAO入力、3V3、振動時の電圧降下。電池側でモーターを含めて平均電流を測れば、同じ電流をもう一度足さない。基板側で測る場合は電圧と変換効率を含めた電力で換算する。

平均電池電流 = 測定区間の消費電荷 / 測定時間
基板入力電力 = 基板入力電圧 × その端子で測った電流
電池からの必要電力 ≒ 基板入力電力 / 電源変換効率 + モーター側平均電力

1. GATT

上記128-bit UUIDは今回の試作のために新規生成した値。既存の標準サービスではない。両側で同じ値を使う。 接続時はサービスを探索、StatusのNotifyを有効化、最初はUNAVAILABLEを送る。サービス／属性が一致しなければ自動駆動しない。

2. Command：10バイト

Offset 長さ 名前 値
0 1 version 1
1 1 state 0=CLEAR（検出なし）、1=CAUTION、2=DANGER、3=UNAVAILABLE
2 2 sequence uint16。新しい指示ごとに+1、65535の次は0
4 2 ttl_ms uint16。初期版は1000だけを受理
6 2 distance_mm 0〜65534。未取得は65535（FF FF）。危険度判定はスマホ側
8 1 flags bit0=床高さが深度から推定された、bit1=手動テスト、bit2〜7=0
9 1 reserved 0

距離は補助情報。FWは距離からstateを再計算しない。CLEAR/UNAVAILABLEのdistanceはFF FFとする。手動テスト時も同じバイト形式を使い、flags bit1を立てる。

iOS送信側

  • 250ms周期を提案。状態が変わったら送信を優先する。送信直前に最新の検知可能状態と深度の鮮度を確認する。
  • 1つのWriteが処理中なら次の状態は最新1件だけ保持し、古い中間状態を積まない。
  • 音声の再通知タイマーと独立させる。同じ状態を再送するときも新しいsequenceを使う。
  • 600msより古い有効深度、明示的カメラエラー、無効姿勢、カメラ停止、背景移行、警告機能OFFはUNAVAILABLEとする。OFFをCLEARと表現しない。
  • 有効な深度で2フレーム連続した注意／危険を採用する案。CLEARも有効な検出なし2フレームで採用。無効な結果で継続回数を進めない。250ms再送も検知フレーム数に数えない。
  • UNAVAILABLEは継続判定を待たず即時。新しい有効状態になるまでは過去の危険度を再利用しない。
  • 閾値・連続判定・TTLは試作値であり、反応時間の保証ではない。

FW受信側

  1. 長さ10、version=1、state範囲、ttl=1000、予約ビット／バイトを検証。不正は状態と受信期限を更新しない。
  2. 接続ごとにsequenceの基準を初期化。初回は受理。
  3. 2回目以降はdelta=(new-old) mod 65536で、1〜32767だけを新規受理。同一seqは重複、32768〜65535は古いとして駆動状態も期限も更新しない。
  4. 受理した時点の単調増加時刻を保存し、受理stateへ移行。同じstateなら振動パターンの位相はリセットせず、期限だけ更新。
  5. 更新から1000ms経過、またはBLE切断を検出したら危険振動を停止し、UNAVAILABLEへ。
  6. 古いパケットの再到着を新しい指示として扱わない。Write responseはBLE層の応答で、実振動の検出を意味しない。

電源再投入・接続直後のGPIOはLOW。手動テストから自動へ戻す際はUNAVAILABLEを経由する。暗号化／Bondingは未決定なので、公開環境で認証済み制御ができる仕様とは扱わない。

3. Status：10バイト

Offset 長さ 名前 値
0 1 version 1
1 1 applied_state 現在FWが採用している0〜3のstate
2 1 error_flags bit0=TTL切れ、bit1=不正パケット検出。以降0
3 1 gpio_level 現在のGPIO3出力、0=LOW／1=HIGH
4 2 last_sequence 最後に受理したsequence。未受理時は0＋state=UNAVAILABLE
6 4 uptime_ms uint32、FW起動からの単調増加時刻。約49.7日で周回
  • 有効Command受理時、状態変更時、不正パケット受信時、接続中のTTL切れ時にNotifyする。
  • last_sequenceは受理確認用。gpio_levelはGPIO出力の状態であり、モーターの実振動を検出した値ではない。
  • 不正パケットフラグは次の有効Command受理でクリア。TTL切れも次の有効Command受理でクリア。
  • 電池残量・電池電圧は含めない。追加するなら測定回路とパケット版を設計する。
  • iOSの時刻とuptime_msを直接引き算しない。送信→Status受信はiOS内の単調時計で計測する。

4. 振動出力

MODE=0、IN2=0を固定し、GPIO3→IN1だけを制御する。HIGHはOUT1=H/OUT2=L、LOWはHi-Z。

state 出力案
CLEAR LOW固定
CAUTION 150ms HIGH、850ms LOWの繰り返し
DANGER 200ms HIGH、150ms LOWの繰り返し
UNAVAILABLE 危険通知パターンを停止。検知不能へ遷移したときだけ50ms HIGH、100ms LOWを3回の通知案

検知不能の通知案は利用者が注意・危険と区別できるかを確認して確定する。起動直後は振動しない。同じUNAVAILABLEの更新・再検出ごとに再生しない。故障や電池切れなら振動通知自体も出せないため、アプリの状態表示と併用する。

今回の追加で特に直す境界

  • HeadLevelAnnouncerは音声の再通知制御。ここからだけBLE送信すると5秒間隔などに制限されるため、深度結果から独立して外部通知状態を生成する。
  • hit == nilだけでは検知不能と検出なしを区別できない。無効姿勢・深度欠損・停止・最新フレーム時刻を持つ状態へ拡張する。
  • HeadLevelGeometry.axes(...) == nil時は現在hit=nilの結果を返す。この結果をCLEARへ変換しない。
  • カメラ側はnil結果をonDepthへ転送しない経路がある。最後の有効フレーム時刻だけでなく、明示的な取得エラーも外部状態へ伝える。
  • App/JunctionGuideApp.swiftは背景移行でstore.pause()を呼び、カメラ等を停止する。前面復帰後は新しい深度を得るまで検知不能とする。
