# 小倉・戸畑の道路データ

- データ: `Data/kokura-network.json`、`Data/tobata-network.json`
- 出典: © OpenStreetMap contributors / ODbL 1.0
- 原本: `Data/raw/kokura-osm.json`、`Data/raw/tobata-osm.json`
- 取得クエリ: `Data/raw/kokura-query.txt`、`Data/raw/tobata-query.txt`
- 抽出矩形（0.4）: 北緯33.8775–33.8925、東経130.8710–130.8900（小倉駅の南北・紫川の両岸・小倉城周辺）
- 戸畑の抽出矩形: 北緯33.8680–33.9310、東経130.8040–130.8710（戸畑区の行政境界全体と約150–180mの余裕）
- 取得日時・OSM基準時刻: ネットワークJSONの`acquiredAt`、`version`。
- 現在のネットワーク: 2365地点・3364区間・5実験接続点（区間の内訳：footway 1864、tertiary 512、unclassified 463、service 190、pedestrian 117、residential 79、primary 74、secondary 29、tertiary_link 20、path 15、primary_link 1）。
- 戸畑ネットワーク: 5886地点・8560区間・5実験接続点（区間の内訳：unclassified 3577、tertiary 1388、service 1334、footway 1043、residential 706、secondary 193、path 146、primary 124、tertiary_link 20、pedestrian 19、secondary_link 10）。実験接続点は戸畑駅周辺、戸畑区役所周辺、九工大前駅付近、戸畑キャンパス正門付近、キャンパス南側。
- 戸畑区の行政境界は、国土数値情報を変換した[Geoshapeの2023-01-01境界GeoJSON](https://geoshape.ex.nii.ac.jp/city/geojson/20230101/40/40105A1968.geojson)で外接矩形（北緯33.8695925–33.92948691、東経130.80574278–130.86934186）を確認した。戸畑抽出矩形の東端は小倉抽出矩形の西端と同じ東経130.8710で、境界線は共有するが面積を持つ重複はない。共有境界線上は現行の配列順（小倉、戸畑）により小倉を選択する。
- 戸畑の取得時に157連結成分を検出し、最大成分（14941 OSMノード）を保存した。第2成分（1355ノード）は北西側の港湾・工業地域（外接矩形：北緯33.896710–33.926224、東経130.804003–130.818184）に集中し、最大成分への歩行可能なOSM接続がないため現行方針どおり除外した。
- `Scripts/benchmark_network.swift`をRelease最適化で実行したApple Silicon Mac上の参考値は、戸畑JSON読み込み51.19ms、道路照合p50 1.21ms / p95 1.73ms、通常経路p50 2.27ms / p95 2.35ms、矩形端からのオフロード経路p50 8.44ms / 最大11.41ms。`tobata-network.json`は7,706,373 bytesで、旧版の860,121 bytesから約6.85MB増加した。この計測では空間インデックスは追加せず、実機iPhoneのDeveloperModeでも経路計算時間と位置更新中の負荷を再確認する。
- 0.3の旧データ（footway/path/pedestrianのみ、298地点・400区間）は`Data/archive/`に原本・加工データ・クエリを残した。

0.4では、歩行用の`footway/path/pedestrian`に加え、歩行者が通行する一般道（`living_street/residential/service/unclassified/tertiary/secondary/primary`と各link、`track`）を取得した。歩道の有無・幅・車道との分離は区別しておらず、車道由来の区間の`conditions`にその旨を記録している。`foot=no/private`、`access=no/private`（`foot=yes`等の例外を除く）、トンネル、屋内、階段、`corridor`、`area=yes`、ドライブスルーは除外した。

紫川の横断を保つため、`bridge`付きで`layer`が1以下の区間は含め、`layer=1`として記録する。それ以外の非地上階層（橋でない`layer=1`、`layer<0`、2以上）と`level`付きの区間は除外した。階層未記載の区間は現地未確認とし、地上と保証しない。横断・施設接続も未確認。最大の連結成分を選んだ。OSMにない接続を見た目から作っていない。

次数2の頂点は、同一OSM way・名称・属性の場合だけまとめ、道路の中間形状を保持する。分岐や属性変更で区間を分ける。区間IDは元wayと両端OSM nodeを含む。道路名がない区間は「名称未登録の歩行区間」、地点名がない場合は「接続点＋ID末尾」を明示的なアプリ内識別名として使用する。現地の目印名を創作していない。

歩行一方通行は`oneway:foot`から取得し、車両の`oneway`を歩行に転用しない。この取得器は完全なOSM経路エンジンではない。時間条件、ゲート、幅、路面、横断信号、すべてのaccess例外を解釈していないため、屋外評価前に対象経路を現地で絞る必要がある。

目的地は、小倉駅南側・京町・魚町・小倉城付近・紫川東岸の座標候補に近いネットワーク地点（候補座標から4〜20m）を実験接続点として選んだ。戸畑は戸畑駅周辺、戸畑区役所周辺の接続点を追加し、九工大前駅付近、戸畑キャンパス正門付近、キャンパス南側と合わせて5地点とした。候補座標からの距離は34.5m以内。いずれもOSM上の接続点であり、施設入口へ接続できたと説明しない。抽出範囲全体のすべての道路へ対応しているわけではなく、保存された区間だけが対象。

## 利用条件と表示

[OSMの帰属・ODbL](https://www.openstreetmap.org/copyright)をアプリに表示する。MapKitの標準の法律表示を隠さない。加工ネットワークはOSM由来のデータとしてODbLを維持し、取得原本と加工方法を保存する。ODbLをアプリのSwiftソース全体のライセンスと混同しない。

Apple地図の形状をトレースして道路データへ取り込んでいない。重ね合わせの位置ずれは未評価。

[北九州市道路台帳数値基図](https://data.bodik.jp/dataset/401005_dourodaichosuuchikizu)は利用候補を調査したが、今回のネットワークには未使用。認定道路に限られ、完成した歩行グラフとみなせない。[国交省の歩行空間ネットワーク仕様](https://www.mlit.go.jp/sogoseisaku/soukou/sogoseisaku_soukou_tk_000056.html)は整備の参考。

## 更新

`python3 Scripts/build_network.py --region kokura`または`--region tobata`は、地域ごとの保存済み原本を再加工する。原本がない場合は停止し、`--fetch`を付けたときだけOverpass APIへ取得に行く。再取得時は既存の原本・クエリ・加工データをタイムスタンプ付きで`Data/archive/`へコピーしてから新しい版を作る。現行アプリに自動取得・更新APIはない。

アプリは両方の道路網をバンドルし、現在地を含む地域へ自動で切り替える。設定で手動選択もできる。地域間の経路は作らず、選択中の道路網外は対応範囲外として扱う。報告ファイルも道路網IDごとに分け、従来の`real-reports.json`は小倉用としてそのまま利用する。

更新後は区間ID対応、連結成分、向き、目的地、閉鎖時の迂回を検査する。現行保存はネットワーク版が違うと案内を保留し、旧報告をそのまま保持する。報告のID移行は自動では行わない。

0.4では、版不一致時に設定から次のどちらかを利用者が確認して選べる。どちらも元ファイルを`*-backup-*.json`へ移動し、削除しない。

- 「同じ区間IDの報告だけ引き継ぐ」：新しい道路データに同じIDの区間がある報告だけを新しい版で保存し直す。
- 「旧報告を退避して新しい道路版で開始」

0.4の区間分割は0.3と異なるため、旧報告の多くは同じIDを持たない。対応しない報告は現地で再登録する。

部分選択は該当区間全体の表示・登録・除外。複数選択は接続する集合に限り、一つのJSON書き込みで保存する。道路データ、報告がないこと、過去の観測のいずれも安全の根拠ではない。
